# Restricted shared hosting and later migration — 2.3.2

The normal source installation keeps runtime, backup/authentication files and sessions outside the web root. This remains the preferred deployment. The individually generated shared-host package explicitly opts into a second profile for hosts whose PHP process cannot write outside htdocs. It is not an automatic fallback.

The package contains public application files under `htdocs/`, an individual profile in `htdocs/config/hosting.php` and a private installation key outside htdocs in `INSTALL-KEY.php`. Only the SHA-256 hash of this random 256-bit token is stored in the public profile. No accounts, database credentials or business records are bundled. The PHP key file exits with HTTP 404 if accidentally uploaded; nevertheless keep it offline. Do not share the archive publicly.

## Preparation and protection

Use HTTPS. Upload all htdocs contents including its .htaccess, then open prepare-host.php. An owner-key and CSRF protected session creates only harmless probes, profile ownership metadata and directory denial rules. The browser must observe actual HTTP 403 for both a text and PHP probe before enabling Continue. It uses the host's existing same-origin browser cookies, allowing the provider's anti-bot cookie to work. Missing authorization, wrong keys, expired sessions, changed paths/rules and non-403 results are rejected. Credentials and application signing keys are not generated before activation.

The proof records the exact profile, physical path, document root and root-rule hash. Every application bootstrap verifies the root denial rule, exact directory rules and binding; missing or changed files prevent app use and require the owner key to recheck protection. Probe files are removed after successful preparation. Existing unrelated directories and symbolic-link targets are rejected. The installer separately verifies the key, CSRF, HTTPS, empty accounts and authenticator enrollment, then seals itself.

**This mode relies on Apache/LiteSpeed honoring .htaccess.** The browser reports HTTP results under owner authorization; this is not an independent server-side attestation or continuing external monitor. Changing server configuration to ignore all .htaccess rules cannot reliably be detected from PHP by reading the unchanged files. Do not enable directory listings or serve PHP as text. Before changing web-server software, recheck protection on a staging copy. Filesystem permission bits depend on the provider and are not a substitute for HTTP denial rules. A purchased host with storage outside the web root is preferable for real business records.

Database credentials, the master encryption/signing key and authenticator secrets are PHP-guarded files, in addition to the root and directory HTTP denial rules. Saved integration configuration and backups remain encrypted. Raw native PHP session records use the provider's normal session service outside the public root; the preparation, installer and app reject a native files-session path inside the public web directory. The profile does not create public session files.

## Moving an existing installation

First take an encrypted in-app backup plus a separate protected copy of the entire installation, uploaded files, database export, installation key and the complete `nsc-private-…` directory. In-app backups exclude hosting credentials, runtime keys and authenticator secrets. Do not reinstall over existing business data. Pause writes during the final migration, and test a separate copy first.

If keeping the same protected profile: preserve the exact profile and random directory, copy all files including hidden rules, import the database on the new host, and update the guarded runtime/database.php credentials privately. Path or document-root changes invalidate the proof. Open prepare-host.php over HTTPS, enter the existing private installation key and repeat both denial checks. Existing installed.lock remains; successful rechecking returns to the app without creating replacement accounts.

For the preferred outside-root deployment: make private runtime and private material directories outside the new document root. Copy the **contents** of the protected `runtime/` into the new runtime directory and of protected `private/` into the new private directory. Preserve every key byte and installed.lock. Keep the `settings.key.php` and `totp-ID.key.php` filenames; the app also reads these guarded formats outside the public root. Update the database credentials privately. Remove `config/hosting.php` from the new site's public files and configure `NIKXOR_RUNTIME_DIR`, `NIKXOR_PRIVATE_DIR` and `NIKXOR_SESSION_DIR` with the new absolute private paths (or use the documented standard var layout). Restart with fresh private sessions. Once the copied installation is tested, remove the old public protected directory from the new host. Do not expose both deployments for simultaneous writes.

Make the private directories writable by the new host's PHP account; copying by FTP/container tools can change ownership. Prefer directory mode 0700 and private-file mode 0600 where supported. Test login and central MFA, both business boundaries, a representative purchase/sale, invoice QR verification, encrypted settings and backup/restore on the staging copy. Preserve the original master key to keep old QR signatures valid. If the public domain changes, update the saved HTTPS origin and Google callback registration; previously printed QR URLs still point to the old domain and need a controlled redirect to remain usable. Configure cron/mail/AI/Google separately according to the new host's services. Nothing here restricts the app to ProFreeHost.

## Existing-site correction in 2.3.2

An account without CREATE VIEW could previously stop at migration 015. Financial report sources now use the same correlated cancellation filter as derived queries and require no database view. Existing views are not dropped. The incremental repair package replaces only 14 PHP files and preserves config/hosting.php, root/directory .htaccess, runtime/private keys, uploads and database records. Merge the htdocs contents rather than replacing entire folders. After uploading all patch files, allow the host opcode cache to revalidate and open the sign-in page to resume the pending migrations. It does not create replacement accounts or reset passwords.

## Package generation

From the source checkout, run `python3 bin/package-shared-host.py /absolute/private/path/release.zip`. Each run creates a new unique profile/key and refuses to overwrite an existing archive. Generate a new profile for a **fresh** installation only. Never replace an existing installation's profile with one from another release ZIP. For updating an installed site, preserve config/hosting.php, the protected directory, uploads, keys and database; stage and review the update first.
